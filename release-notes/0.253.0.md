# 0.253.0

## Fixed: moving one note made your sync client re-upload the whole folder

Moving a note to another Stashpad — with the destination picker or the move
command — rewrote the frontmatter of notes that had nothing to do with the
move, including archived ones. Every one of those rewrites is a file your sync
client has to upload again, so a single move could turn into dozens of uploads.

The cause was the step that keeps the `parentLink` and `children` recovery
links honest after a move. It refreshed *both entire folders* rather than the
notes the move actually touched — correct, but far more work than the move
warranted, and it grew with the size of the folders rather than with the size
of the move.

A move can only invalidate a known, small set of links: the notes that moved,
the parents they left, and the parent they joined. That is now the set that
gets rewritten.

Measured on a 27-note folder: a move that previously wrote **15** files now
writes **3** for a single note, or **6** for a note carrying three nested notes
with it — in each case exactly the notes whose links genuinely changed. Nothing
about the recovery links themselves has changed; they are still written, still
complete, just no longer accompanied by collateral.

## Fixed: the home note listed itself as one of its own children

The `children` recovery list on a folder's home note included a link back to
the home note. Harmless to click, but wrong, and it padded every home note's
list with a self-reference. Now excluded.

## Undo restores the recovery links too

Undoing (or redoing) a cross-Stashpad move put the files back immediately, but
left `parentLink` and `children` pointing at the folder the notes were no
longer in, until you next opened one of the two folders. Undo and redo now
repair those links themselves.
