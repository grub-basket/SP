# 0.490.0

Performance release. Stashpad on a very large vault — particularly one living on a
network or department drive — was spending minutes of every session re-reading things
it already knew. This release stops that, and adds a way to push whatever background
work remains outside working hours.

The headline: **discovering folder encryption keys no longer scales with the size of
the vault.** On a 537-directory test tree with 20ms of injected per-operation latency,
startup key discovery went from 1,678ms and 537 directory listings to 182ms and
**zero** directory listings. Extrapolated to a 10,000-directory share at 100ms per
operation, that is roughly 143 seconds per scan becoming about 1.3 seconds — and the
scan used to repeat every ten minutes.

## Performance

### Folder encryption keys are remembered instead of hunted

`.stashkey` files are dotfiles, which Obsidian's in-memory file index does not track.
The only way to *discover* one was to list every directory in the vault — and that ran
at startup, every ten minutes, and after every sync burst, **even when encryption had
never been set up**.

Stashpad now remembers which folders hold a key and verifies them with one read each.
Cost is proportional to the number of keys, not the number of directories.

Key discovery remains complete. Four independent checks guarantee it:

- A schema epoch, so every existing install performs one full scan before the fast
  path is used at all.
- Reconciliation against encrypted content. `.stashenc` and `.stashmeta` files *are*
  indexed by Obsidian, so "which folders hold encrypted content" is a free in-memory
  question; any folder that the remembered set cannot account for triggers a targeted
  on-disk probe, and a full scan if that probe comes up empty.
- Negative answers are still verified against disk — the folder and then each
  ancestor — before they are believed.
- If every remembered folder fails to read (an unmounted share, a stalled sync), the
  remembered set is treated as unusable rather than as proof the keys are gone.

New command **"Search the whole vault for folder passwords"**, with a matching button
in Settings → Maintenance, for the case where a key arrives somewhere nothing was
watching — a restored backup, or a folder copied in from outside. It performs the old
exhaustive scan, and is intentionally manual because on a network drive it is slow.

### Background maintenance window

Settings → Maintenance → **Background maintenance window**. Stashpad runs five
background sweeps over the vault; this adds one window they can be made to respect,
plus a checkbox per sweep deciding whether it does.

- **Whenever it's due** — the default, and unchanged behaviour.
- **Only outside my working hours** — set working hours and days; maintenance is
  blocked during them. A live description always spells out the resulting window, so
  there is no arithmetic to do.
- **Only when I'm idle** — after a chosen number of minutes without input, or any time
  the Obsidian window is in the background.
- **Never automatically** — only when explicitly run.

Covered sweeps, each listing its cadence and what deferring it costs: the folder
password re-scan, auto-tidy of Stashpad tabs, the auto-import sweep, author-file
seeding, and archive exclusion registration.

Every switch defaults to off, so upgrading changes nothing until a sweep is opted in.
The window governs **background maintenance only** — work that can be rebuilt later.
It never delays saving a note, settings, undo state, or anything explicitly requested.

New command **"Run deferred background maintenance now"**, plus a **Run now** button,
which is the only way anything runs in "Never automatically" mode.

### Opening a folder no longer repeats work per tab

Creating a Stashpad folder's infrastructure — the folder, its Home note, the
import/export subfolders, the null-parent migration — is idempotent and belongs to the
folder, but was tracked per view. Opening a second Stashpad tab on the same folder
therefore repeated every one of those disk operations for no effect. It now runs once
per folder per session, and is re-run if the folder is deleted or renamed. A duplicate
existence check on the same path during startup was removed at the same time.

### Fewer disk operations per note

Creating one note went from 13 adapter operations to 9 in the steady state. The
savings are redundancy: the note-history store was re-creating the same directory
chain on every capture, and folder existence was being re-checked for a folder already
confirmed moments earlier. Nothing about what gets written, or when it becomes
durable, changed.

## Fixes

- Loading a draft now targets the Stashpad tab in front rather than the leftmost one.
  Reported as "the button does nothing" — it was working, into an off-screen tab.
- "Reveal or open Stashpad" and deep-link navigation had the same leftmost-tab
  problem, and deep links additionally had their tab-preference order backwards.
- The welcome dialog could stack two copies when Stashpad was opened within a couple
  of seconds of launch on a fresh vault. It is now single-instance.
- Drafts remember the note they were started under, show it in the drafts list as
  `under "<title>"`, and return there when reopened. Drafts whose origin no longer
  exists stay put.
- Every Stashpad-spawned tab now returns focus to where it came from when closed.
- Note-history captures could silently lose a version if the history directory was
  removed underneath them — the write failed into a best-effort error handler. Writes
  now recover by re-creating the directory and retrying.

## Under the hood

Three build-time checks were added so mistakes that have shipped more than once cannot
ship again:

- Picking a single Stashpad tab out of the workspace with `[0]` or `.find()` — which
  means "leftmost tab", never "the tab in front" — is now rejected outside the one
  module allowed to do it. That bug had shipped three times in features written years
  apart.
- Opening a new tab without wiring return-on-close is rejected.
- Building fails if another branch has already claimed the version in `manifest.json`.
  Two branches writing the *same* version string merge without a conflict, so the
  usual safeguard never fires; this had happened twice.

Also: development-harness consolidation, an isolated-instance testing driver shared
across projects, and internal performance notes.

Housekeeping: `package.json` indentation restored after a version-bump script
reformatted it, and one version renumbered after two lines of work independently
claimed the same number — the collision that prompted the check above.

## Notes

The performance figures above were measured with per-operation latency injected to
model a network share. Operation *counts* are exact; wall-clock figures for a
particular drive are arithmetic from measured per-operation costs rather than
observations on that hardware.
