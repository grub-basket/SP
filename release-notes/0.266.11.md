# 0.266.11

A new Stashpad no longer starts life with two home notes, the list stops
re-rendering on a loop, and the debug trace finally reports which device and
which Obsidian version produced it.

## Setting up a Stashpad creates one home note, not two

Creating a Stashpad wrote its home note as `Home.md`, while the view looks for
the folder-tagged `Home-<folder>.md` and decides whether one already exists by
asking Obsidian's metadata cache for each file's `id`. The cache has not parsed
a file written moments earlier, so it reported "no home note here" for a home
note already on disk — and created a second one. Both carried `id: __root__`,
which is what the duplicate-ID check reported on a brand-new folder.

Three changes, since any one alone leaves a gap:

- the home filename is now defined **once** and shared, rather than restated in
  three places — two of them drifting apart is what caused this;
- the view checks the **path** before creating, which needs no cache at all;
- and a home note written under the older bare name is adopted by reading its
  frontmatter from disk, so an existing folder cannot duplicate during the same
  cold window.

Verified across all three setup routes: **Set up fresh**, **Set up with demo
content**, and a folder carrying a legacy `Home.md` opened with a cold cache.
Each ends with exactly one home note.

A folder that already has two home notes stays that way — this prevents new
ones rather than merging old ones. Use **Discard** in the duplicate-ID modal to
remove the extra; it keeps the one holding your content.

## The list stops re-rendering in a loop

Breadcrumb titles are warmed in the background when a crumb's note has no
heading and no cached body, and that warm ends by asking for a re-render — so a
render was scheduling the next render. That is only safe while "is this note
still cold?" reliably becomes false after warming. When something kept an entry
cold, the two fed each other indefinitely: traces from a phone show renders
every ~83 milliseconds, with identical geometry, for as long as the view stayed
focused deep enough to have breadcrumbs.

Each crumb is now warmed at most once per view, so a second warm is impossible
and the loop cannot form regardless of what kept the entry cold.

## Text selection in the composer

Text controls inside Stashpad now declare `user-select: text`. Obsidian's mobile
styling disables text selection across the app — that is what allows a sideways
drag to open a sidebar — and its editor re-enables it for the editing surface.
Stashpad's composer inherited the disabled value and never re-enabled it, so a
control you type into could not be selected from.

## The debug trace says where it came from

Three fixes to the diagnostics, all of which cost real time before:

- the header carries the **Obsidian Sync device name** when there is one. A user
  agent cannot tell two iPhones apart; the name you gave the device can.
- it reports **Obsidian's version** correctly. It was reading a property that
  does not exist, so every trace collected so far said `Obsidian ?`.
- the render scheduler records **which code asked for the render**. The previous
  attempt assumed Chrome's stack-trace format and returned an empty string on
  iOS, where the format differs — so the one field meant to identify the cause
  was blank in exactly the traces that needed it.
