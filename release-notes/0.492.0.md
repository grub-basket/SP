# 0.492.0

Bug-fix release with one performance improvement. The headline is a fix for a
settings bug that quietly deleted configuration: **the four built-in buttons on
every note row — Edit, Focus, Reply, React — could disappear entirely, and the
settings section meant to control them showed nothing to bring them back.**

The cause was not in the buttons. Stashpad's settings collision guard, which stops
one device overwriting another's settings, was reverting *every* one-time migration
on the first save of a session. Anyone whose buttons vanished gets them back
automatically on the next launch.

## Fixes

### Item buttons no longer vanish from the note row

0.475.0 moved the four built-in row buttons into the configurable `itemButtons`
list so they could be reordered and hidden. On installs whose `data.json` already
carried an explicit empty `itemButtons` — the default from 0.320.0, when that list
held only buttons the user had added — the newly seeded built-ins were discarded on
the next save, leaving a note row with no buttons at all and no way to restore them.

The seed itself was correct. The collision guard undid it:

- The guard decides "did this device change the key, or did another one?" by
  comparing the in-memory value and the on-disk value against a baseline.
- That baseline was captured *after* the one-time migrations had already run, so a
  migration was invisible to the comparison: the in-memory value matched the
  baseline (reading as "this device did not change it") while the on-disk value did
  not (reading as "another device did").
- The guard therefore adopted the stale on-disk value back, undoing the migration.
- The companion flag `itemButtonsSeeded` was absent from disk, so the guard skipped
  it and it persisted as set — which permanently blocked the seed from re-running.

The baseline is now captured from disk, before the migrations, for exactly the keys
a migration rewrote. A migration is recognised as a local change and is written.

This fixes the whole category, not just the row buttons. Every one-time migration
was subject to the same revert — including the cross-vault stamping default, the
editor-shortcut correction, and the legacy composer-draft cleanup.

The narrowing matters and is deliberate: keys the loader merely *normalises* —
keybindings gaining new defaults, invalid saved searches being dropped — keep the
previous baseline, so the rule introduced in 0.211.1 ("another machine changed this
while we were loaded, take theirs") still applies. A migration is a real local
edit; re-deriving a value is not.

### Row buttons are restored automatically, once

An install currently sitting on an empty list gets the four built-ins back on the
next launch, behind a one-time flag. Hiding every button remains a valid choice and
survives a restart — the repair runs once and never second-guesses a later decision.

### A missing `itemButtons` entry falls back to the defaults

An absent setting now resolves to the built-in buttons rather than to an empty list.
Absent means lost, not chosen, and the empty-list fallback was overriding the
defaults on every path that can drop the key — including the config-folder split,
where the list lives in `menus/menus.json` while its flags live in `data.json`.

### The Item buttons settings section always lists the built-ins

Previously the section listed only buttons that were switched on, so turning one off
removed it from its own editor — and turning all of them off left an empty section
with nothing to click.

- Each built-in shows an eye to hide it, instead of a cross that made it vanish.
- A hidden built-in stays listed, greyed, with an eye to show it again.
- **Restore the default buttons** brings all four back in one click, and keeps any
  command added to the row rather than replacing the list.
- With everything hidden the section now says so, and says what to click.

The star menu and the right-click menu are unchanged.

## Performance

### Structure snapshots read their file once per write instead of twice

Every write of the per-folder recovery sidecar `.stashpad-structure.json` read the
same file twice — once parsed, for merging with the previous snapshot, and once raw,
for the rotation that keeps the prior copy. Six filesystem operations where four
will do, which on the network drive measured in 0.489.0 (300–600ms per operation)
cost roughly 0.6–1.2 seconds per write.

A single read now returns both the raw bytes and the parsed value: six operations
become four, verified live.

This is not a cache, which is why it is safe. Nothing is retained between
operations, so there is no window in which stale structure data could be written —
the concern that led 0.489.0 to leave this alone. It is also strictly more correct
than reading twice: the old code could read different bytes for the merge than for
the rotation if a sync landed in between, and rotate a copy that never matched what
was merged.

## Internal

These do not change how Stashpad behaves; they are recorded for completeness.

- Parallel development lanes now reserve their version number when a lane is
  claimed, and the build fails if a lane builds under a number another lane
  reserved. Two branches writing an identical version string merge without a
  conflict, so nothing downstream caught it.
- The version-collision check recognises each repository's own version-subject
  convention rather than assuming this one's.
- Documentation and changelog updates accompanying the above: the 0.490.0
  close-out, the snapshot-read and version-gate follow-ups, a corrected comment
  header on the version gate, and the write-up of the item-buttons investigation.
