# 0.257.0

## Fixed: "Move to…" moved the wrong note

Right-clicking a note and choosing **Move to…** moved whichever note was
selected in the list, not the note you right-clicked.

Because a list row is always selected, this was never harmless — it just looked
correct whenever the note you right-clicked happened to be the selected one.
Right-click an *unselected* row and choose Move, and a different note moved.

It was most obvious from the header of the note you are currently inside, which
is where it was reported: that note isn't in the list at all, so choosing Move
on it always moved one of its children instead. Asking to move a parent and
watching a child leave is a confusing thing to undo.

Every other item in that menu already acted on the note you right-clicked —
Copy, Clone, Fork, the task actions. Move was the only one that didn't, and it
now behaves like the rest.

## The home note can no longer be moved

Found while fixing the above. Nothing prevented a folder's **home note** from
being reparented — it was simply unreachable, since the home note is never the
selected row. Pointing Move at the right-clicked note made the home note's own
header a way to get there, and a folder whose root note hangs off another note
is not a state Stashpad should be able to reach.

Moving the home note is now refused with an explanation, wherever the attempt
comes from — the menu, a drag, a keyboard shortcut, or the command palette.
