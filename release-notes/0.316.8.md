# 0.316.8

One fix, at the root of the mobile scroll problems that arrived with list
virtualization.

## Virtualized note list — row-anchored scrolling

Large folders render only a window of rows and size the rows *above* it from an
average row-height estimate. That estimate is refined as more rows get measured,
and nothing translated the scroll position when it changed: the top spacer grew
or shrank under a fixed pixel `scrollTop`, so the same pixel suddenly showed
different rows. A single late re-render could grow the list by thousands of
pixels and leave the view stranded far above the bottom; the same mechanism
produced the open-folder flicker (three paints, three estimates) and "reacting
to a note scrolled me". Every earlier fix in this line was fighting that
downstream.

- **Renders are anchored to a row, not a pixel.** A re-render now hands the
  virtualized list the row that was at the top of the viewport (and its offset)
  and resolves it to a pixel only *after* the height estimate is recomputed —
  the one point where that pixel is correct. The `follow-cursor` and legacy
  "restore previous scroll" paths use the translated value too, so no path
  restores a stale pixel into a re-estimated list.
- **The estimate is frozen during scrolling.** It is recomputed only on
  explicit updates (mount / pin / reveal), never on a scroll tick — so content
  can't slide under a finger mid-gesture, and there is never a programmatic
  scroll write during a fling.
- **True sticky-bottom.** While the view is pinned to the newest note, every
  window update lands on the bottom, and a reaction chip growing a row re-pins
  on the spot — late body measurement or a reaction can no longer leave the
  list a few rows short. A swipe up clears the pin as before.
- **The anchor is re-asserted as async layout settles.** Note bodies in the
  rows just above the viewport render lazily after a paint and grow; the
  browser's own scroll anchoring only partly compensated. The anchor is now
  re-applied over the settle steps (the same machinery the restore /
  scroll-to-id paths use), converging on the exact offset.
- **Window rebuilds can't stall.** The scroll tick fires on
  `requestAnimationFrame` *or* a short timer, whichever comes first, and the
  settle loop re-windows directly after its own scroll writes — so a throttled
  or delayed frame can no longer leave the bottom spacer on screen instead of
  the newest note.
- Reveal-row placement (`virtEnsureIndex`) is resolved the same row-anchored way.
