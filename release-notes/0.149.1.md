# 0.149.1

Builds on 0.147.0's deep links with a paste-to-open path, UI polish, and two
title/filename fixes surfaced along the way.

## Deep links — paste to open (0.147.1)

- New command **"Open Stashpad link (paste a deep link / URL)"** and a 🔗 button in
  the view's actions cluster. Paste an `obsidian://stashpad?…` link into a small
  dialog and it jumps to the note — for apps that won't render `obsidian://` URLs
  as clickable links. The same action is also in the ⚡ actions menu.
- The dialog pre-fills from the clipboard when it already holds a Stashpad link,
  and has an explicit **Paste** button for platforms where clipboard auto-read is
  blocked.
- Accepts a full `obsidian://stashpad?…` URL or a bare `folder=…&note=…` query;
  unresolvable links report a clear notice rather than doing nothing.

## Deep-link UI polish (0.147.2 / 0.147.3 / 0.148.1 / 0.148.2)

- The open-link control uses a link icon.
- The paste dialog's input fills the row with the **Paste** button beside it.
- The 🔗 button shows on mobile too, next to the ⚡ actions button.
- The breadcrumb row now spans the full width of the view, and on desktop the
  filter bar above it lines up edge-to-edge with it.

## Fix — focused note showed its title instead of its body (0.148.0)

- When you drilled into a note, the focused-note header at the top could show the
  note's *title* instead of its *body* (for notes whose body wasn't cached yet).
  It now always renders the body.

## Breadcrumb / title reads the note's content (0.149.0)

- The breadcrumb, tab title, note pickers, and title-sort now use a note's **first
  body line** as its title, instead of its filename. Previously a note whose
  filename was a short slug (e.g. `grand.md`) showed just "grand" even though its
  body was a full sentence. Notes now read by what they say, not what their file is
  named. A per-crumb length cap still keeps long titles tidy.

## Filename repair for hand-renamed notes (0.149.1)

- The "rebootstrap" maintenance action and the automatic on-edit rename now also
  repair a note whose file was manually renamed so its name lost the trailing id —
  they fall back to the note's own id to rebuild a correct filename. Files that
  merely carry an unrelated `id` field are never touched.
