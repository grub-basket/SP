# 0.255.0

## Diagnostic modes switch themselves off after a week

**Performance profiling** and **Debug trace** are meant to be turned on for as
long as it takes to capture a problem, then turned off. They are easy to forget
about, and neither is free while running — profiling records timing on every
render, read and write, and the debug trace watches scroll position for two
seconds after a colour change, a to-do toggle, or entering select mode. On a
phone that is a real cost, and left on it is paid indefinitely for a
troubleshooting session that ended months ago.

Each mode now remembers when it was switched on and turns itself back off after
seven days. When that happens you get a notice saying which mode was turned off
and where to turn it on again — a setting that changes itself quietly is worse
than one left on, because the next capture would come back empty with no
visible reason why.

Two things it deliberately does *not* do:

- **It does not reset when Obsidian restarts.** Much of what these modes exist
  to catch is startup and mobile behaviour that needs a restart to reproduce.
  Clearing on launch would be simpler and would break the main use case.
- **It never clears the debug trace buffer on a timer.** That buffer already
  holds a fixed number of recent lines and is discarded when Obsidian reloads.
  Wiping it periodically would add nothing and could throw away a capture in
  the moment between reproducing a bug and copying it out.

If a mode is already on when you update, it is left running and its week starts
now, so an upgrade can't interrupt a capture in progress.

The check runs when the plugin loads. An Obsidian window left open for weeks on
end won't expire a mode mid-session — that is intentional, since flipping the
setting underneath someone who is actively capturing is the worse outcome.
