# 0.211.8

This release closes a full data-loss audit of the codebase. Most of it is
invisible in normal use: it removes ways Stashpad could have lost notes,
attachments, encryption keys or settings in situations involving crashes,
sync, multiple devices, partial failures, or undo used in an unusual order.

Anyone using encryption, cross-vault copy/paste, or `.stash` import/export
should update.

## 0.211.2 — importer polish

- The per-row colour picker in the paste importer lists colour **names**
  (Red, Orange, Amber, Lime, Green, Blue, Purple, Pink, Magenta) instead of
  raw hex codes. macOS draws a `<select>` as a native menu with no swatches
  and no styling, so a list of hex values was unreadable. The names come from
  the same table Stashpad already uses to parse `[color: …]`, so the picker
  and the parser cannot disagree. Colours with no known name still show hex.
- The import command reads **"Import pasted text into Stashpad (paste →
  nested notes)…"**, so the palette entry says where the text will go.

## 0.211.3 — encryption keys and cross-vault cut

- **Permanently deleting old key material now refuses when a folder still
  needs it.** "Retire the old keyfile" already refused if any folder's key
  lived only in that keyfile. The irreversible "Permanently delete" beside it
  did not, so confirming it could destroy the only copy of a key and leave
  that folder's encrypted notes unreadable for good. It now performs the same
  check — and reports the refusal, which it previously swallowed silently
  after the user had typed a confirmation phrase.
- **A folder's key file is never removed before its replacement exists.**
  Writing `.stashkey` could delete the current file and then fail to put the
  new one in place, leaving the folder with no key at all. Writes now stage to
  a temporary file, verify it byte-for-byte, keep the previous key as a
  backup, write over the target rather than deleting first, verify again, and
  restore the backup if anything is wrong. This also adds the read-back check
  that changing a folder password previously lacked.
- **A cross-vault cut only offers to delete the originals after a complete
  paste.** The acknowledgement that tells the source vault "these arrived
  safely" was sent whenever the import finished without raising an error —
  including when it had skipped notes. The source vault could then offer to
  delete originals that never made it across. It is now sent only when every
  note arrived and nothing was skipped.

## 0.211.4 — undo safety, import and export

- **Undoing a split can no longer delete the split-off half without
  restoring the original.** Undo looked the original note up by the file path
  it had at the time of the split. Stashpad renames a note when its first line
  changes, so after a retitle that lookup failed — and the undo went ahead and
  trashed the new note anyway. Undo now finds notes by their stable id and
  stops safely if the original cannot be found, leaving everything in place.
- **Redo can no longer re-delete a note that has been restored and edited.**
  The Undo button on the delete notice and the undo history were two
  independent controls sharing one flag, so a particular sequence could send
  redo to trash a live, edited note and then restore a stale copy over it.
  Using the notice's Undo now retires the matching history entry, and redo
  re-reads each note and refuses to delete one whose contents have changed.
- **Import and export no longer stall on unusual note bodies.** The pattern
  used to find attachment embeds scanned quadratically over text containing
  many unclosed `![[` sequences: about 0.75s for 60KB and 12s for 240KB, on
  the main thread. It is now linear (under 5ms for 960KB).
- **Two attachments with the same filename export correctly.** An export
  identified attachments by filename, so `Assets/A/diagram.png` and
  `Assets/B/diagram.png` collapsed into one file in the bundle and both notes
  pointed at it — the second note silently carried the first note's image.
  Attachments are identified by their full path now, and each gets its own
  entry.
- **Two notes sharing an id in one bundle no longer collide.** Both were
  written with the same new id, and since the outline is keyed by id one of
  them vanished from the list. Each note now gets its own identity, checked
  against ids already in the folder and ids issued earlier in the same import.
- **A failed note no longer aborts the whole import.** One note that cannot
  be written is reported as a skipped entry while the rest import normally,
  instead of stopping everything partway. A failed cross-vault paste also no
  longer claims nothing was changed, since notes may already have been
  written.

## 0.211.5 — attachments and the render cache

- **Deleting a note keeps attachments that other notes still use.** "Also
  delete attachments" removed every attachment the note referenced, with no
  check for whether anything else pointed at them, so deleting one note could
  break the images in another. Shared attachments are now kept, and the notice
  says how many.
- **Undo can restore every attachment a delete removed.** The delete removed
  attachments listed in a note's frontmatter as well as those embedded in its
  body, but the undo snapshot captured only the embedded ones — so a
  frontmatter-only attachment was deleted and could not be brought back.
  Delete and undo now work from the same list, and an attachment that cannot
  be read is left in place rather than deleted into a gap.
- **A locked note's text can no longer reappear in the render cache.**
  Removing an entry from the cache did nothing if the note was still being
  rendered at that moment, so the render could finish afterwards and write the
  full text and rendered HTML back to disk — after encryption had removed the
  readable copy. Removal is now recorded, and a late render is refused.

## 0.211.6 — merge, trash, split and repeating tasks

- **An interrupted merge can still be undone.** Merging recorded its undo
  entry only after every note had been merged and removed. If something failed
  partway, the kept note had been rewritten and some notes were already in the
  trash with nothing to undo. The undo entry is now recorded before any note
  is removed, and an interrupted merge says so and points at undo.
- **Restoring from the trash keeps the item when the restore is
  incomplete.** The trash bundle is the only copy of the notes inside it, and
  it was deleted after every restore regardless of the outcome. It is now kept
  whenever anything failed to restore, so the restore can be retried.
- **Redoing a split no longer creates a duplicate.** Redo recreated the
  split-off note if nothing was found at its original path — but a note that
  has been retitled lives at a different path, so redo could add a second copy
  carrying the same id. Redo now checks the id.
- **A repeating task no longer spawns two copies of the next occurrence.**
  The background check decided from a cached view of each note, so two checks
  close together, or two devices, could each create a successor. Closing an
  occurrence is now a single claim against the file itself, and only the first
  one creates the next occurrence.

## 0.211.7 — locking, clipboard, snapshots and renames

- **Locking a note no longer leaves both an encrypted and a plaintext copy.**
  Background writes of the recovery fields Stashpad keeps in frontmatter could
  land in the moment between the lock recording a note's state and removing
  the plaintext, which correctly kept the note but had already written the
  encrypted copy — so a later restore produced a duplicate. Those writes are
  now finished before locking begins.
- **Pasting notes from another vault asks the first time.** The clipboard
  payload is ordinary clipboard data, so any page copied from can produce one
  and label it with any vault name, including the user's own. The first paste
  from a given name now confirms and says plainly that the name cannot be
  verified. Accepted names are remembered.
- **Hiding filenames no longer leaves the titles in a recovery file.** The
  per-folder structure snapshot stores note titles so a damaged folder can be
  repaired. Locking with filename-hiding removed the note but left its title
  in a snapshot written moments earlier, and the retained previous generation
  kept it indefinitely and synced it. Titles of notes that are no longer
  present are now removed from both.
- **Renaming a folder keeps its ordering.** The per-folder order and sort
  files were written by path, so a rename could write them back into the old
  folder, recreating it, while the new folder never received the ordering.
  Both now follow the rename.
- **Editing a note straight after retitling records the contributor again.**
  Contribution tracking was keyed by file path, so Stashpad's own automatic
  rename made the next edit look like the first time that note had been seen
  and the stamp was skipped. Renames are now tracked.

## 0.211.8 — remaining fixes

- The folder unlock path checks the unwrapped key's length before using it,
  rather than accepting a corrupt or tampered key file's contents.
- The order and sort files are no longer deleted when they exist but cannot
  be read. An unreadable file was treated the same as an empty one, which
  removed it and lost every ordering it held.
- A structure snapshot that cannot be read no longer discards the repair
  records it held; the retained previous generation is used instead. An
  unreadable snapshot is also no longer copied over that previous generation,
  which used to cost both copies at once.
- Export archive entries keep valid filenames for non-ASCII names, which
  could previously be cut mid-character.
- `.stash` export gives two notes with the same filename distinct entries, so
  neither can be dropped from the bundle.
- OKF bundles rewrite embedded attachment links to point at the bundle's own
  `_attachments/` folder. The files were included but the links still referred
  to the original vault, so nothing outside that vault could display them.
